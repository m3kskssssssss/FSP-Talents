# Логика подбора

Код: `server/matching/score.ts` (чистые функции), `server/services/matching.ts` (выборка, снимок, фильтры). Тесты: `tests/unit/score.test.ts`, `tests/integration/matching.test.ts`.

## 1. Ввод потребности

Работодатель заполняет форму или вставляет текст вакансии. Текст разбирается так:

- **LLM (RouterAI)** со структурированным выводом по Zod-схеме (`response_format: json_schema`). Если схема не поддерживается — JSON-режим, валидация и одна попытка исправления. Кеш по хешу входа, таймаут 20 с.
- **Фолбэк без LLM**: словарь стеков (~65 навыков с алиасами RU/EN), регулярные выражения для грейда (в том числе по фразе «опыт от N лет»), зарплаты («от 150 000 до 250 000 ₽», «180–260 тыс.», «200k-300k»), формата и города.

Результат показывается в форме для подтверждения. Без полной вилки сохранить потребность нельзя (422).

## 2. Жёсткий фильтр (правило 5)

В пул попадают только кандидаты, у которых:

- есть **активная категория из теста** нужной специализации и грейда (соседний грейд — отдельным блоком «Близкие кандидаты»);
- `visibility = visible`, аккаунт не удалён;
- действует согласие на обработку ПДн.

Самоописание и резюме не добавляют кандидата в пул. Они влияют только на ранжирование, и такие навыки всегда помечены «заявлено».

## 3. Скоринг (детерминированный, объяснимый)

match = round(100 · Σ wᵢ · cᵢ), где все cᵢ ∈ [0, 1], а веса заданы в `MATCH_WEIGHTS` (`server/config.ts`):

| Компонента | Вес | Как считается |
|---|---|---|
| `test` | 0.40 | (балл/30 − 12) / 18, обрезка в [0, 1]; при среднем доверии ×0.9 |
| `stack` | 0.22 | Среднее по навыкам потребности: подтверждён тестом 1.0, косвенно подтверждён тестом (SQL → PostgreSQL) 0.8, из резюме 0.6, заявлен 0.5, нет данных 0 |
| `fsp` | 0.14 | raw / (raw + 1.5), см. ниже |
| `salary` | 0.10 | Ожидания ≤ верха вилки → 1; выше — штраф 1 − 3·превышение (не исключение); ожиданий нет → 0.75 |
| `formatCity` | 0.07 | Совпадение формата 1; гибрид ↔ другое 0.6; офис ↔ удалёнка 0.25; другой город при офисе/гибриде ×0.35/0.5 |
| `freshness` | 0.07 | 0.6·свежесть теста (1 до 90 дней, затем экспоненциальный спад) + 0.4·активность профиля |

### Бонус ФСП с убывающей отдачей

Вес достижения = место × доверие × этап × свежесть, где:

- место: 1-е = 1.0, 2-е = 0.75, 3-е = 0.6, 4–10 = 0.3, 11–50 = 0.12, участие без места = 0.02;
- доверие: реестр ФСП 1.0 > организатор 0.8 > репозиторий 0.6 > заявлено 0.2;
- этап: финал 1.0, окружной 0.8, региональный 0.6;
- свежесть: полураспад 3 года.

raw = Σ(top-5 весов) + 0.5 · ln(1 + Σ остальных весов).

**Одна победа весит больше сотни участий без мест** — это проверяет тест: 1.0 против 5·0.02 + 0.5·ln(1 + 95·0.02) ≈ 0.63. Кандидат без истории в ФСП не исключается и не «невидим»: компонента равна 0, в доводах — «Истории в ФСП нет» (правило 6).

## 4. Объяснения

Доводы собираются **из тех же компонент**, что и скор, с весом вклада. Берутся 2–4 «за» и 1–2 «против». Примеры — лучший и худший кандидат одной подборки из `validation.md` (сгенерированы кодом, не вручную):

> **77 match** — потребность «Разработчик микросервисов (Junior), java, kubernetes, mysql», релевантен по скрытой истине: да
> + Уверенно сдал тест Junior: 27.3/30
> + Java подтверждён тестом
> + Ожидания 80 000 ₽ — в пределах вилки
> + MySQL — косвенно подтверждено тестом
> − Часть стека не подтверждена тестом

> **38 match** — потребность «Разработчик микросервисов (Junior), java, kubernetes, mysql», релевантен по скрытой истине: нет
> + Тест Junior сдан: 19.4/30
> + MySQL — косвенно подтверждено тестом
> − Нет данных о навыках: Java и Kubernetes
> − Ожидания 160 000 ₽ — выше вилки на 14%

**LLM только перефразирует** (кнопка «Доводы человеческим языком»): один вызов на подборку. Проверка «никаких новых фактов»: в ответе не должно быть чисел, которых нет в исходных доводах, количество доводов должно совпасть. Если проверка не прошла или LLM недоступен, остаются шаблонные формулировки.

## 5. Снимок и уточнение без потери подборки

- «Подобрать кандидатов» сохраняет `searches.base_snapshot` — упорядоченный список `{profileId, match, near}` на момент поиска.
- Фильтры (грейд, стек и «только подтверждённые тестом», «только с ФСП», порог теста, город, формат, соседний грейд) применяются **поверх снимка**. Снимок не меняется, и это проверено тестом. «Сбросить» = пустые фильтры = исходная подборка.
- Если кандидат после поиска скрыл профиль или отозвал согласие, он выпадает из выдачи (приватность важнее), счётчик показывает это.
- «Поиск по базе» работает тем же движком, но без потребности: специализация, грейды, стек, бюджет, формат, город.
- Избранное (`shortlist`), пагинация, без N+1: пул загружается тремя запросами (категории + профили, навыки, достижения).

## 6. Что видит работодатель (правило 2)

Карточка кандидата (`toCard`) **не содержит контактов**. Имя маскируется («Анна Н.») до принятия приглашения или отклика. Тест проверяет, что в JSON ответа подборки нет ни email, ни телефона, ни Telegram, ни фамилии.
