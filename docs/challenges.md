# Регулярные задачи от работодателей

ТЗ: «система периодически предлагает кандидату задачу от работодателя — решить её или предложить подход; это поддерживает профиль в актуальном состоянии и даёт работодателю свежий сигнал о кандидате».

## Как это работает

| Шаг | Кто | Что происходит |
|---|---|---|
| 1 | Работодатель, `/employer/challenges` | Пишет короткую задачу для специализации и, по желанию, грейда. Выбирает способ проверки: **по эталону** (система сравнивает ответ) или **«предложите подход»** (оценивает сам, 0–3) |
| 2 | Система | Кандидату с активной категорией выдаёт **одну** задачу не чаще раза в 14 дней (`CHALLENGE_CONFIG.periodDays`). Выдача ленивая — при входе в кабинет, без cron. Кандидат получает уведомление |
| 3 | Кандидат, `/candidate/challenges` | Видит компанию, условие и способ проверки. Отвечает или пропускает без штрафа |
| 4 | Система / работодатель | Ответ по эталону проверяется сразу (нормализация: регистр, пробелы, `ё`, десятичная запятая). Открытый ответ попадает работодателю в «Ждут оценки». Работодатель видит замаскированное имя и ответ, **без контактов** |
| 5 | Подбор | Хороший результат (≥ 2/3) за последние 90 дней показывается в подборке доводом «Свежий сигнал: решил задачу работодателя …». Ответ обновляет `lastActiveAt` — от него считается компонента «свежесть» скоринга |

## Почему так

- **Грейд не меняется.** Грейд даёт только квалификационный тест (ответ экспертов FTT.4, VS.5). Задача — сигнал актуальности, а не экзамен.
- **Адресно, а не на всю категорию** (ответ E09). Задачу получает конкретный кандидат, по одной за период.
- **Задача не расходится по рынку.** Из подходящих задач выдаётся наименее показанная (`ORDER BY exposure`), поэтому кандидаты одной категории получают разные задачи. Один кандидат никогда не получает одну задачу дважды (уникальный индекс). Работодатель может закрыть задачу, если считает её «засвеченной».
- **Эталон не уходит на клиент.** `expectedAnswer` читается только в `submitAnswer`, API кандидата его не отдаёт (покрыто тестом).
- **Пропуск без штрафа.** Кандидат не обязан решать: пропуск только сдвигает следующую задачу на период.
- **Вес небольшой.** Задача по эталону проще слить, чем адаптивный тест. Поэтому результат влияет только на свежесть (7% скоринга) и на довод в карточке, но не на категорию и не на порядок снимка подборки.

## Где в коде

| Что | Где |
|---|---|
| Таблицы `challenges`, `challenge_assignments` | `server/db/schema.ts`, миграция `drizzle/0007_challenges.sql` |
| Выдача, проверка, оценка, сигнал | `server/services/challenges.ts` |
| Параметры | `CHALLENGE_CONFIG` в `server/config.ts` |
| API | `GET/POST /api/v1/challenges`, `POST /challenges/{id}/close`, `GET /challenges/submissions`, `POST /challenges/submissions/{id}/grade`, `GET /me/challenges`, `POST /me/challenges/{id}/answer`, `POST /me/challenges/{id}/skip` |
| Довод в подборке | `searchResults` в `server/services/matching.ts` |
| Тесты | `tests/integration/challenges.test.ts` |

В демо-данных у `employer@demo.ru` четыре задачи, два ответа ждут оценки, а `strong@demo.ru` при открытии раздела «Задачи» сразу получает новую.

## Развитие

- Плановая выдача по расписанию (cron) и напоминания о незавершённой задаче.
- Задачи с исполнением кода в той же песочнице, что и тест, с параметризацией варианта под кандидата — тогда эталон не сливается.
- Калибровка сложности задач по ответам, как у шаблонов теста, и учёт результата в весах ранжирования.
